# kgc-bench — SPARQL-Generate against RML engines and SPARQL Anything

A reproducible benchmark of [SPARQL-Generate](https://github.com/sparql-generate/sparql-generate)
for knowledge graph construction:

| | Question | Instrument | Entry point |
|---|---|---|---|
| **RQ1** | Is SPARQL-Generate conformant to RML? By hand-written queries, and by an automatic translation written in SPARQL-Generate itself? How do the RML engines fare on the same cases? | the RML test cases (RMLio/rml-test-cases, CSV/JSON/XML tracks; kg-construct/rml-core and the five RML modules), RDF dataset isomorphism | `python -m harness.conformance` |
| **RQ3** | How do time and peak memory compare with the RML engines and SPARQL Anything, as sources grow? | GTFS-Madrid-Bench (official CSV mapping, and `gtfs-inverted`, its IRI-valued branches inverted), synthetic nested JSON and XML, flat CSV; KGCW Challenge 2024 data | `python -m harness.perf` |

Results: [`results/results.md`](results/results.md) (generated by `python -m harness.report`
from the CSV files of `results/`). Timings in it are **provisional** until re-measured on a
quiet machine: `results/machine.json` records the machine and its load.

In the conformance runs, each RML engine is run as a user runs it: with its default
options, N-Quads output, from a directory that holds the case's mapping and input
documents (never its expected outputs); the base IRI is given to the engines that take
one (RMLMapper, FlexRML and BURP `-b`, RMLStreamer `-i`); SDM-RDFizer is told
`new_formulation: yes` for a mapping in the namespace of the W3C KG-Construct CG. One limit
for all: 120 s and the memory cap per process.

**The judge** (`harness/conformance.py`), the same for every engine:

- a case that expects an error passes when an error is raised: the process exits with a
  non-zero code, times out, is killed at the cap, or logs an error (an ERROR, FATAL or
  CRITICAL line, a Java exception, a Python traceback), **or writes an empty output (or
  none)**; otherwise it fails ("no error raised"). The empty output counts as an error
  reported because some engines report errors so: SDM-RDFizer creates its output file first
  and stops at an error it detects (SDM-TIB/SDM-RDFizer#128). The strict count, where an
  empty output is no error raised, is kept in the column `status_strict` of
  `results/conformance.csv`;
- a case that expects no error passes when the output (and every expected target file) is
  isomorphic to the expected one, as an RDF dataset. **Lenient rule**: the output alone
  counts, whatever the exit code or the log; an engine that raised an error but wrote the
  expected output passes (detail "error raised, output correct: ..."). It does not apply
  when the process was killed (time, memory) or wrote no output file.

Cases the lenient rule makes pass (measured 2026-11-26): BURP 18 (12 RML-FNML cases with
the expected output and exit status 1, 6 of rml-test-cases), FlexRML 3, RPT 2,
SDM-RDFizer 1; none for SPARQL-Generate, pysparql-generate, Morph-KGC, RMLMapper,
RocketRML, RMLStreamer.

## Settings

Every engine runs with its default options and the same limits (16 GB of memory, 10 min a
run in the performance runs; 120 s in the conformance runs), except for the settings
below. Each one is either needed to run the engine at all, or what the engine's
maintainers and the published evaluations use.

| Engine | Setting | Why | Source |
|---|---|---|---|

| RocketRML (performance) | `--max-old-space-size` = 75 % of the memory limit | the Node.js counterpart of `-Xmx`: its default heap limit (about 4 GB) is lower than the others' | Node.js documentation |

| RMLMapper (performance) | `-d` (remove duplicates) | every other engine writes each triple once; the KGCW Challenge tool and KROWN run RMLMapper with `-d` (and a heap of 50 % of the RAM) | kg-construct/challenge-tool, `bench_executor/rmlmapper.py`; kg-construct/KROWN |

| FlexRML (conformance) | output given as `./engine-output.nq` | FlexRML 2.x creates the directory of its output and fails on a bare file name | measured |
| Morph-KGC | none (`morph-kgc`); `number_of_processes=4` (`morph-kgc-4p`) | the default is twice the number of CPUs (32 worker processes here): their memory adds up, and on GTFS scale 100 they go over 16 GB; a worker killed by the kernel leaves the pool waiting for ever (recorded OOM, not DNF). With 4, the GTFS scale 10 peak (sum of the workers, 0.96 GB) extrapolates to about 10 GB at scale 100, well under the limit; with 8 (1.57 GB) to the limit itself, with 32 (2.85 GB) to 28 GB | morph-kgc issue #26; measured (below) |

| ShExML | the GTFS mapping in ShExML, generated rule by rule from the official one: the 12 joins written as reference conditions (the parent's IRI from the child's column: the same graph, checked); a helper function strips the scheme of the five IRI-valued columns (the prefix is `http://` or `https://`); an `IF` empty-cell test on the four columns that have empty cells | ShExML has no referencing object map, no IRI from a full IRI value, and writes an empty cell as a literal; its `IF` results are matched by a linear search (quadratic in the rows), hence a test on those four columns only | `scripts/gtfs_mappings.py`; de Vleeschauwer et al., KGCW 2023; ShExML `RDFGeneratorVisitor` |

**Peak memory** is the resident memory of the largest process (GNU `time -v`), or the
private (anonymous) memory of all the processes of the run's scope together when it is
larger (`anon_peak_mb` of `perf-runs.csv`, polled every 0.2 s in the cgroup): a
multi-process engine such as Morph-KGC is counted whole. A run in which the kernel killed a
process at the memory limit is recorded `OOM`, even if it then hung until the time limit.

## Engines not included

The engines that the related work cites and that this benchmark does not run, and why:

- **D-REPR** ([usc-isi-i2/d-repr](https://github.com/usc-isi-i2/d-repr), PyPI `drepr`
  2.11.2, 2023-12-25): its semantic model types literals only with `xsd:decimal`,
  `xsd:anyURI`, `xsd:gYear`, `xsd:date`, `xsd:dateTime`, `xsd:int`, `xsd:string` and
  `geo:wktLiteral` (`drepr/models/sm.py`, `DataType`; another type is refused: "Get
  `xsd:double` while possible values are ..."). The GTFS-Madrid-Bench mapping types 22
  literals with `xsd:double`, `xsd:integer` and `xsd:boolean`: no D-REPR mapping can write
  the reference graph, and its output cannot pass the output check that every engine
  passes. Its only RDF output is Turtle.

## Workload gtfs-inverted

The GTFS-Madrid-Bench data and mapping, with the direction of every IRI-valued branch
inverted: a mapping whose entities are the *objects* of most of their IRI-valued
triples, the shape of an inverted star. The official mapping has 13 triples maps and 86
object maps: 50 literals, 13 `rdf:type` constants, 11 IRIs (6 IRI templates, 5 IRI-valued
columns) and 12 referencing object maps (joins). Each of the 23 IRI-valued triples
`?s p ?o` of the GTFS output is written `?o inv:p ?s`, where `inv:p` is
`<http://transport.linkeddata.es/inverse/LOCAL>`, LOCAL the local name of `p` (the 17
local names are distinct); the literal and `rdf:type` triples are unchanged. No IRI is
minted from a literal, and an empty cell gives no triple, as in GTFS. The inversion is a
bijection: the output has exactly as many distinct triples as GTFS's (395,953 at scale
1), and inverting the GTFS output gives it, triple for triple (checked at scale 1).

- **RML** (`workloads/gtfs-inverted/gtfs-inverted-csv.rml.ttl`): a triples map has one
  subject map, so every inverted branch needs a triples map of its own: **GTFS has 13
  triples maps, gtfs-inverted 36** (the 13 entities, with their literals and `rdf:type`,
  and one per inverted branch, 23). An IRI branch becomes a triples map on the same
  source whose subject map is the branch's object map (a template, or a column with
  `rr:termType rr:IRI`) and whose object is the entity's template. A join is inverted
  with its direction: the triples map reads the parent's source, its subject map is the
  parent's, and its referencing object map points to the child's triples map, the join
  condition swapped; the joins and their values are those of GTFS.
- **SPARQL-Generate** (`gtfs-inverted-csv.rqg`, written by hand): one `GENERATE` per file
  (as for GTFS), one iteration per row, and one template that writes the row's entity as
  the subject of its literals and the object of its inverted branches; the joins are the
  key lookups of the GTFS query.
- **ShExML** and **SPARQL Anything** (`gtfs-inverted-csv.shexml`, `.sa.sparql`) are
  generated by `scripts/gtfs_mappings.py`, the ShExML mapping as for GTFS (one shape per
  inverted branch, the joins as reference conditions), the SPARQL Anything query from the
  GTFS one (its CONSTRUCT template inverted, its WHERE clause unchanged).

All the files are generated from the official mapping by `scripts/gtfs_mappings.py`,
except the SPARQL-Generate query; `tests/test_gtfs_inverted.py` checks that they are
current and that they write the same 23 inverted branches. The data are those of
`gtfs` (`data/gtfs/<scale>`); default scales 1 and 10. Every output is checked like
GTFS's, by its fingerprint against the reference engine's.

Output check at scale 1 (2026-11-26, one untimed run each, 600 s limit): the fingerprint
of Morph-KGC's output is that of SPARQL-Generate (hand-written, translated and
translated-tau), pysparql-generate (hand-written, translated-tau), Morph-KGC with 4
processes, RMLMapper, SDM-RDFizer, SPARQL Anything and ShExML (run again without the
time limit: 512 s, against 117 s on GTFS). Not equal, as on GTFS: FlexRML
(`xsd:integer` on untyped numeric values). Errors: RPT 2.0.0-rc7, whose translation
fails on a subject map with `rml:reference` (ClassCastException, as in conformance case
RMLTC0019a), and pysparql-generate on the 0.3.0 translation (as on GTFS: `SUM(...) > 0 ||
RAISE(...)` in the `HAVING` of the header checks raises although the left side is true).
DNF at 600 s, as on GTFS: RocketRML, BURP, RMLStreamer; ShExML too. RMLMapper, DNF on GTFS,
finishes: the inverted self-join of SHAPES points to a triples map whose subject uses the
join column only.

The translation of an RML mapping for the `*-translated` engines is not timed with the run;
its own time limit is `KGC_BENCH_TRANSLATION_TIMEOUT` (seconds, default 600). gtfs-feeds at
K = 1000 has 13 000 triples maps, about a quarter of an hour of translation with
rml2sparql-generate 0.5.4.

## Other versions, suites of another date, diagnostics

Measuring an engine at another version, or against the suites as they were when it was
released, changes no pin and writes nowhere but where it is told:

- `KGC_BENCH_PIN_<KEY>=<value>` overrides the pin `KEY` of `versions.env` for one run (the
  engine is looked up under `engines/` by its usual name, e.g. `rmlmapper-7.3.3.jar`;
  a Python engine is taken from `PYTHONPATH`); the version recorded is the overriding one;
- `scripts/suites_at.sh DATE DEST` exports each suite at its last commit before `DATE`
  (never after the pin) and `KGC_BENCH_THIRD_PARTY=DEST` points the harness at them;
- `KGC_BENCH_DIAGNOSTIC=literal-sources` (structured sources of the CG rewritten as path
  literals) or `rpt-iri-sources` (the source blank nodes of RPT's generated queries turned
  into IRIs) tell one defect of an engine from the rest; such runs are labelled
  `[diagnostic: ...]` in the version column and are never published results.

## Output check and disk space

Every output of the performance runs is checked at every scale and then deleted: its
**fingerprint** is computed in a stream, without loading it (`harness.rdfcompare.digest`):
Jena `riot` rewrites it in canonical N-Quads (one spelling per term: escapes, `xsd:string`,
whitespace), `sort -u` deduplicates it with a bounded buffer and zstd-compressed spill
files, and the SHA-256 and the number of the sorted lines are kept (`digest` and `triples`
of `perf.csv`). An output whose fingerprint is not the reference's (Morph-KGC, else
SPARQL-Generate; measured in the same command, or stored in `perf.csv`) is `wrong-output`,
not a measurement. The escapes of RDFC-1.0's canonical N-Quads are applied to riot's output
(control characters), so that the two forms below are the same lines.

An output with **blank nodes** goes, once deduplicated, through **RDFC-1.0**, the W3C RDF
Dataset Canonicalization (https://www.w3.org/TR/rdf-canon/), by
[rdf-canonize](https://github.com/digitalbazaar/rdf-canonize) 5.0.0 (pinned in
`versions.env` with the SHA-256 of its npm tarball; `scripts/rdfc/rdfc.js`, on the pinned
Node.js). It labels the blank nodes canonically, and the canonical quads are sorted and
hashed the same way: the fingerprints of outputs with and without blank nodes compare.
rdf-canonize passes 63 of the 64 evaluation tests of the W3C suite (`tests/rdfc10`; the
64th asks for SHA-384), with its limit on deep iterations lifted. RDFC-1.0 works in memory
and can be costly on pathological graphs: it runs in a capped scope (the memory limit of a
run, a heap of 75 % of it) with a time limit of 600 s. Over a limit there is no
fingerprint: the triple count alone is compared (`equivalent` = `count`, the reason in the
note of the row). `--keep-outputs` keeps the outputs (debugging).

A workload may ask for a **normalised fingerprint** (attribute `normalise`): the canonical
N-Quads then go through `harness/ntnormalise.py`, which removes two differences that RML-Core
allows or recommends, and no other. In an IRI, the percent-encoded UTF-8 of a non-ASCII
character is replaced by the character (the IRI-safe version of a template value keeps
such characters; an engine that writes the URI-safe version gives the same IRI after the
filter); an `xsd:double` literal takes its canonical form. Real data need it (GTFS France);
GTFS-Madrid-Bench does not.

The disk then holds one output at a time, plus the spill files of its sort. On
GTFS-Madrid-Bench an N-Triples output takes about 180 bytes a triple: about 70 MB at scale
1, 0.7 GB at 10, 7 GB at 100 and 70 GB at 1000, plus about a fifth of that in compressed
spill files. Free space needed on the file system of `KGC_BENCH_WORK`: 1 GB at scale 1,
2 GB at 10, 10 GB at 100, 100 GB at 1000. RMLStreamer, which keeps duplicates, may write
more than its fingerprinted output: up to about 31 GB in 600 s at scale 1 (deleted when the
run is stopped).

## Memory safety

Every process the harness starts (engines, translations, triple counts) runs in a
transient systemd scope with a memory cap ([`harness/sandbox.py`](harness/sandbox.py)):

```sh
systemd-run --user --scope --slice=agents-kgcbench.slice \
    -p MemoryMax=<cap> -p MemorySwapMax=0 -p OOMPolicy=continue \
    choom -n 1000 -- /usr/bin/time -v -o <report> <engine command>
```

- `MemoryMax` caps the process tree, `MemorySwapMax=0` forbids swapping: an engine that
  outgrows the cap is killed at once by the kernel, instead of driving the whole machine
  into swap (where systemd-oomd may kill the user session);
- `OOMPolicy=continue` keeps the scope when the engine is killed, so that
  `/usr/bin/time -v`, inside it, still reports the peak resident memory;
- the run is recorded with status `oom` (`OOM` in `perf.csv`, with the cap in the
  note), and the harness goes on. With the time limit (10 min), the memory limit (16 GB)
  is the definition of a viable run: over either, the solution is not viable at that
  size, is never replayed, and is not tried at larger scales;
- all scopes share the slice `agents-kgcbench.slice`, whose own `MemoryMax` bounds the
  sum of the processes run in parallel; its name puts it under `agents.slice`, which, on a
  machine shared with other jobs, can bound the sum of all of them;
- the OOM score of every engine process is 1000 (`choom`): if the kernel runs out of
  memory anyway, it kills the engine, not the desktop;
- a run over its time budget has its whole scope killed (`systemctl --user kill`), with
  every process the engine started.

The cap is `--mem-cap` (every harness command), else `KGC_BENCH_MEM_CAP`, else `20G`;
the slice cap is `KGC_BENCH_MEM_TOTAL`, else `20G` for a slice that has none (a command
never lowers it). `--mem-cap none` runs uncapped.
`scripts/capped.sh <command>` runs any other command (a build, an ad hoc run) under the
same cap. This needs a systemd user session with the memory controller delegated (the
default on current Linux distributions).

## rml2sparql-generate

The translation of RML into SPARQL-Generate is itself a SPARQL-Generate query, maintained
in its own repository, [rml-to-sparql-generate](https://github.com/sparql-generate/rml-to-sparql-generate),
and fetched at the commit pinned in `versions.env`. The benchmark runs its optimised translation (the pinned
commit) and, as a check, its direct translation without rewritings (engines
`*-translated-tau`).

## Workloads of other repositories

The harness is a Python package (`pyproject.toml`, `harness`): a repository of workloads
depends on a tag of kgc-bench (`pip install "kgc-bench @ git+https://github.com/sparql-generate/kgc-bench@<tag>"`),
not on a copy. Its workloads join the registry `harness.workloads.ALL` by the entry points
of the group `kgc_bench.workloads` of its own `pyproject.toml`,

```toml
[project.entry-points."kgc_bench.workloads"]
my-workloads = "my_package.workloads:WORKLOADS"
```

or by `KGC_BENCH_WORKLOADS=my_package.workloads[:WORKLOADS],...`; the object named is a
workload, a list of them, or a function that returns them (`harness.workloads.load_external`).
A workload may give its scales (`default_scales`) and ask for the normalised fingerprint
(`normalise`). `KGC_BENCH_ROOT` is the checkout of kgc-bench whose `engines/`,
`third_party/` and `versions.env` the installed harness uses. `scripts/patched_runs.sh` runs
the engines one at a time, each with its proposed patches when they are built
(`scripts/patches/build.sh`, branch `patched-engines`), else as released.

## Layout

```
versions.env            pins: test suites, translator, workloads, engines, JDKs
scripts/                fetch_testcases.sh, fetch_engines.sh, build_sparql_generate.sh,
                        build_pysparql_generate.sh, gtfs_data.sh, fetch_kgcw.sh,
                        capped.sh, campaign.sh
conformance/hand/       hand-written SPARQL-Generate queries, one per test case
                        (rml-test-cases, rml-core)
workloads/              mappings and queries of the performance workloads
harness/                conformance.py (RQ1), perf.py (RQ3), memory.py, engines.py,
                        workloads.py, rdfcompare.py (the oracle), sg.py (the
                        SPARQL-Generate CLI), sandbox.py (memory caps), report.py
results/                conformance.csv, perf.csv, perf-runs.csv, machine.json, results.md
```
