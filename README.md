# kgc-bench — SPARQL-Generate against RML engines and SPARQL Anything

A reproducible benchmark of [SPARQL-Generate](https://github.com/sparql-generate/sparql-generate)
for knowledge graph construction:

| | Question | Instrument | Entry point |
|---|---|---|---|
| **RQ1** | Is SPARQL-Generate conformant to RML? By hand-written queries, and by an automatic translation written in SPARQL-Generate itself? How do the RML engines fare on the same cases? | the RML test cases (RMLio/rml-test-cases, CSV/JSON/XML tracks; kg-construct/rml-core and the five RML modules), RDF dataset isomorphism | `python -m harness.conformance` |
| **RQ3** | How do time and peak memory compare with the RML engines and SPARQL Anything, as sources grow? | GTFS-Madrid-Bench (official CSV mapping), synthetic nested JSON and XML, flat CSV; KGCW Challenge 2024 data | `python -m harness.perf` |

Results: [`results/results.md`](results/results.md) (generated by `python -m harness.report`
from the CSV files of `results/`). Timings in it are **provisional** until re-measured on a
quiet machine: `results/machine.json` records the machine and its load.

## Engines

| Engine | Version | Input | Conformance (RQ1) | Performance (RQ3) |
|---|---|---|---|---|
| SPARQL-Generate (Java) | 2.4.1, the GitHub release asset (checksum pinned); the 2.1.0 release; a local build of `../sparql-generate` with `KGC_BENCH_SG_JAR=head` | hand-written queries, or translated by `rml2sparql-generate` | modes `hand`, `translated` | yes |
| pysparql-generate | a commit of `../pysparql-generate` exported by `scripts/build_pysparql_generate.sh` (never the working copy; commit recorded) | hand-written queries, or translated | modes `hand`, `translated` | yes |
| Morph-KGC | 2.10.0 (PyPI) | RML | mode `rml` | yes |
| RMLMapper | 8.1.0 | RML | mode `rml` | yes |
| SDM-RDFizer | 4.7.5.15.4.1 (PyPI `rdfizer`) | RML | mode `rml` | yes |
| RPT (RDF Processing Toolkit) | 2.0.0-rc7 | RML, translated to SPARQL `CONSTRUCT` by `rpt rmltk rml to sparql` | mode `rml` | yes |
| SPARQL Anything | 1.3.0 | SPARQL over Facade-X (`SERVICE <x-sparql-anything:...>`) | no (no RML input) | yes |

In the conformance runs, each RML engine is run as a user runs it: with its default
options, N-Quads output, from a directory that holds the case's mapping and input
documents (never its expected outputs); the base IRI is given to RMLMapper (`-b`), the
only one that takes it; SDM-RDFizer is told `new_formulation: yes` for a mapping in the
namespace of the W3C KG-Construct CG. One limit for all: 120 s and the memory cap per
process. An expected error is raised when the process exits with a non-zero code, times
out, is killed at the cap, or logs an error.

## Test suites

| Suite | Repository (commit pinned in `versions.env`) | Cases | What it tests |
|---|---|---|---|
| `rml-test-cases` | RMLio/rml-test-cases | 117 (CSV, JSON, XML tracks; the SQL tracks need databases) | the legacy RML vocabulary (R2RML + `rml:`) |
| `rml-core` | kg-construct/rml-core | 76 | RML-Core, the W3C KG-Construct CG vocabulary |
| `rml-io` | kg-construct/rml-io | 73 | sources (formats, encodings, compression, NULL values) and logical targets (serialisations, compression) |
| `rml-fnml` | kg-construct/rml-fnml | 22 | functions (FnO, GREL, IDLab functions) |
| `rml-cc` | kg-construct/rml-cc | 35 | collections and containers (`rdf:List`, `rdf:Bag`, `rdf:Seq`, `rdf:Alt`) |
| `rml-star` | kg-construct/rml-star | 18 | RDF-star: quoted triples maps |
| `rml-lv` | kg-construct/rml-lv | 41 | logical views: fields, joins of views |
| `kgc-bench-extra` | this repository (`conformance/extra/`) | a few | minimal cases of this benchmark |

There are hand-written SPARQL-Generate queries for `rml-test-cases` and `rml-core` only:
on the module suites, mode `hand` is N/A. An RML-IO case passes only if every target file
it expects (`dumpN.*`, compressed or in another serialisation: JSON-LD, N3, RDF/XML,
RDF/JSON, Turtle) is written and isomorphic.

All versions and third-party commits are pinned in [`versions.env`](versions.env); the
scripts of `scripts/` fetch them into `third_party/` and `engines/`, which are not
versioned. Every Java engine runs on the same JDK (21) with the same maximum heap. The
version of each engine is recorded with every result row, and the report is labelled
from it.

## Memory safety

Every process the harness starts (engines, translations, triple counts) runs in a
transient systemd scope with a memory cap ([`harness/sandbox.py`](harness/sandbox.py)):

```sh
systemd-run --user --scope --slice=agents-kgcbench.slice \
    -p MemoryMax=<cap> -p MemorySwapMax=0 -p OOMPolicy=continue \
    choom -n 1000 -- /usr/bin/time -v -o <report> <engine command>
```

- `MemoryMax` caps the process tree, `MemorySwapMax=0` forbids swapping: an engine that
  outgrows the cap is killed at once by the kernel, instead of driving the whole machine
  into swap (where systemd-oomd may kill the user session);
- `OOMPolicy=continue` keeps the scope when the engine is killed, so that
  `/usr/bin/time -v`, inside it, still reports the peak resident memory;
- the run is recorded with status `oom` (`OOM` in `perf.csv`, with the cap in the
  note), and the harness goes on. With the time limit (10 min), the memory limit (16 GB)
  is the definition of a viable run: over either, the solution is not viable at that
  size, is never replayed, and is not tried at larger scales;
- all scopes share the slice `agents-kgcbench.slice`, whose own `MemoryMax` bounds the
  sum of the processes run in parallel; its name puts it under `agents.slice`, which, on a
  machine shared with other jobs, can bound the sum of all of them;
- the OOM score of every engine process is 1000 (`choom`): if the kernel runs out of
  memory anyway, it kills the engine, not the desktop;
- a run over its time budget has its whole scope killed (`systemctl --user kill`), with
  every process the engine started.

The cap is `--mem-cap` (every harness command), else `KGC_BENCH_MEM_CAP`, else `20G`;
the slice cap is `KGC_BENCH_MEM_TOTAL`, else `20G` for a slice that has none (a command
never lowers it). `--mem-cap none` runs uncapped.
`scripts/capped.sh <command>` runs any other command (a build, an ad hoc run) under the
same cap. This needs a systemd user session with the memory controller delegated (the
default on current Linux distributions).

## rml2sparql-generate

The translation of RML into SPARQL-Generate is itself a SPARQL-Generate query, maintained
in its own repository, [rml-to-sparql-generate](https://github.com/sparql-generate/rml-to-sparql-generate),
and fetched at the commit pinned in `versions.env`. The benchmark runs its optimised translation (the pinned
commit) and, as a check, its direct translation without rewritings (engines
`*-translated-tau`).

## Layout

```
versions.env            pins: test suites, translator, workloads, engines, JDKs
scripts/                fetch_testcases.sh, fetch_engines.sh, build_sparql_generate.sh,
                        build_pysparql_generate.sh, gtfs_data.sh, fetch_kgcw.sh,
                        capped.sh, campaign.sh
conformance/hand/       hand-written SPARQL-Generate queries, one per test case
                        (rml-test-cases, rml-core)
workloads/              mappings and queries of the performance workloads
harness/                conformance.py (RQ1), perf.py (RQ3), memory.py, engines.py,
                        workloads.py, rdfcompare.py (the oracle), sg.py (the
                        SPARQL-Generate CLI), sandbox.py (memory caps), report.py
results/                conformance.csv, perf.csv, perf-runs.csv, machine.json, results.md
```
